Refresh / Content Opportunity Scoring: A Ranked Action Engine for Content Review

Huma Aslam · Machine Learning Intern, FlyRank AI · 2026

Abstract. With thousands of content pages and limited review capacity, which pages should a content team check first? I built a ranked scoring system combining a hand-written baseline rule with a Random Forest classifier trained on eight observable, pre-decision signals. Evaluated on a client-grouped, leakage-checked split, the model reached Precision@50 of 0.540 versus the baseline's 0.380 - a 1.42x improvement. A separate validation audit found that an ordinary random split overstates this same result by 59.3%, purely from client leakage - a finding that shaped every methodology decision in this paper. The result is directional and decision-support only, not causal.

Introduction / Problem statement

A website can have thousands of content pages and no reliable way to know which ones are quietly losing traffic. Manual review doesn't scale past a handful of pages per cycle, so the real decision this work supports is: given limited reviewer capacity, which pages should a content strategist check first?

The action this ranking feeds is direct: a reviewer opens the top-ranked pages and decides whether to refresh, expand, or leave them. Getting the ranking wrong has a real cost either way - reviewer time wasted on pages that were never declining, or a genuinely declining high-traffic page missed for weeks while it keeps losing visibility.

Data

This work uses the FlyRank ML Internship starter release (content_refresh_anonymized.csv), a public-safe extract of 30,000 content-page rows across 32 anonymized clients, with pre-decision signals only - no product health flags, no post-hoc labels. No client names, domains, or private queries appear anywhere in this paper or the underlying notebooks.

The label used is a proxy, not an observed future outcome: is_declining = (trend_direction == "down"), a rule computed on the current window rather than a genuine past-to-future prediction. This limitation is treated as a first-class caveat throughout, not a footnote.

Excluded by design: the starter release deliberately omits any product decision flags that would leak the answer into the features - confirmed directly in earlier notebook work, where feeding a label-derived signal (trend_pct) into a model pushed Precision@50 to a suspicious 1.000, the signature of leakage rather than a real result.

Methodology

Signal verification, before any model was built

Two candidate signals were checked directly against the data, each with a bucketed table and a one-word verdict, before either went into a scoring rule:

SignalVerdictFinding
Staleness (days since update) vs. decline rateMIXEDDecline rate rises from 51.1% (0–30 days) to 61.1% (91–180 days), then drops to 46.7% at 181–365 days on a much smaller, less reliable sample.
CTR vs. position tierCONFIRMEDMean CTR rises monotonically from 0.150 (deep) to 1.484 (top 3), across all five tiers, each with a large sample (min n=1,319).

The MIXED verdict directly shaped the baseline rule: staleness was only used within the 31–180 day window where the pattern actually held, not as a blanket signal.

Baseline

A hand-written rule combining visibility, moderate staleness, and CTR-vs-tier-expectation: score = impressions_90d × is_moderately_stale × (1 / ctr_vs_tier_avg), with one reason code (STALE_AND_CTR_UNDERPERFORM) and an action label.

Model and features

A Random Forest classifier (300 trees, max depth 8, class-balanced) trained on eight pre-decision features: impressions_90d, days_since_last_update, avg_position, ctr, word_count, engagement_rate, content_age_days, search_volume. Random Forest was chosen over plain Logistic Regression because it can weigh multiple signals against each other and capture non-linear interactions the fixed baseline formula cannot.

Validation design - and what changing it revealed

The model was evaluated under two different split designs, deliberately, to measure how much the validation choice itself matters:

Same model, same data, same metric - only the split design changed.

A naive random row-level split let 31 of 32 clients appear in both train and test, since a client's pages share systematic traits (industry, content style, baseline traffic). That leakage alone inflated Precision@50 to 0.860 - a number that looks excellent but proves nothing about generalizing to a new client.

The honest client-grouped split (GroupShuffleSplit on client_id, 75/25) produced 22,885 train rows across 24 clients and 7,115 test rows across 8 clients, with confirmed zero client overlap. This is the split used for every result reported from here forward.

59.3% - how much the naive split overstated the model's real performance, purely from client leakage.

Results

Model vs. baseline, evaluated on the identical held-out, client-grouped test set.

The Random Forest reached Precision@50 = 0.540 against the baseline rule's 0.380 - a 1.42x improvement in how many of the top 50 ranked pages were genuinely declining, on a split where no client's data crossed between training and testing.

Feature importance and error interpretation

impressions_90d and content_age_days dominate the model's decisions (permutation importance). Notably, days_since_last_update shows negative importance - directly confirming the earlier MIXED signal verdict: staleness alone is not a reliable predictor once other signals are available.

Among false positives (predicted declining, not actually), nearly all shared ctr = 0.0 with small-to-moderate impressions. Among false negatives (real decliners scored lowest), the same ctr = 0.0 pattern appears, but paired with very low impressions_90d. Both error types cluster around the same blind spot: very low-traffic, zero-CTR pages, where the underlying signal is thin either way.

Limitations & honest framing

  • The label is a proxy, computed on the current window, not an observed future outcome - this is directional, decision-support evidence, not a validated forecast.
  • The 1.42x improvement is observed on this dataset and this split; it is not a causal claim about what refreshing a page would do, and does not reflect or attempt to reverse-engineer Google's ranking algorithm.
  • Validation design changes the answer by nearly 60% on this same problem - any reported result (mine or anyone else's) should be read alongside its split design, not in isolation.
  • Both error types concentrate on very low-traffic pages - the model is weakest exactly where the data has the least signal to offer.

Ranked recommendations

The model's decline probability feeds a four-archetype action engine, applied to the full 7,115-page held-out set:

Ranked action distribution across the held-out test set.
ActionShareReason code
Refresh now16.4%HIGH_VISIBILITY_DECLINE_RISK - high traffic, high predicted risk
Review this cycle25.2%MODERATE_REVIEW - worth checking, not urgent
Protect / leave as-is33.7%HIGH_VISIBILITY_STABLE - high traffic, low predicted risk
Monitor only24.8%LOW_TRAFFIC_MONITOR_ONLY - too little visibility for a confident call
  1. Adopt the grouped-split model over the hand-written rule for weekly review-queue generation - the 1.42x gain is real and verified on a held-out, client-grouped split.
  2. Route the "Monitor only" 24.8% to a separate, lighter-touch track rather than the main ranked queue - this is exactly where the model's errors concentrate.
  3. Never validate a refresh model on a random row split - the 59.3% inflation found here should be treated as a standing warning for any future iteration of this work.
  4. Do not use staleness as a standalone flag outside the 31–180 day window - confirmed independently by both the signal check and the model's own negative feature importance.
  5. Revisit the label definition next - moving from a current-window proxy to a genuine past-90-day-features → next-30-day-outcome split would convert this from a directional signal into an actual forecasting validation.
